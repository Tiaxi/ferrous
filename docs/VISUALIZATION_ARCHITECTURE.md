# Visualization architecture

## Playback and analysis

Playback owns audio output and publishes transport position and track identity. The position is the pipeline's own, with the `CLOCK_MONOTONIC` time the engine read it and whether it advances from there; the UI's `PlaybackClock` extrapolates it once, and the transport bar, spectrogram, waveforms, level meter, and MPRIS all read that clock. It does not forward unused PCM to the visualizations. Analysis opens independent decoders, preserving native sample rate and timestamped frame positions. Symphonia decodes the formats it supports; a file it cannot open, or opens but decodes no audio from, is read with GStreamer, as raw AC-3 and DTS always are. Symphonia cuts an MP3's encoder delay and padding, and an Ogg Vorbis file's pre-skip, as playback does, so frame 0 is the first sample that plays; Symphonia 0.5 cannot do this for AAC. Exact seeks decode codec preroll and trim to the requested frame. A spectrogram column is a fixed time rather than a fixed number of samples, so a track scrolls at the same pace whatever its sample rate: at zoom 1, columns are 1024 samples of 44.1 kHz apart for rates that are multiples of 11,025 Hz, and 1024 samples of 48 kHz apart for every other rate, rounded to a whole sample (`src/analysis/column_hop.rs`). The two families scroll about 9% apart, as 44.1 and 48 kHz always have; the FFT size stays a number of samples. Each chunk carries its session's rate and column hop, and Qt derives the zoom from the reference hop of that rate. Spectrogram sessions align their FFT windows to an absolute sample grid, each centred on its column's time, so a sound shows in the column of the time it plays; timestamp gaps become bounded silence batches and overlaps are trimmed. Every channel of a view gets every decoded frame, also when the decoder's channel count differs from the file header's or changes mid-stream; a mono stream fills every channel. If the sample rate of a stream that GStreamer decodes changes mid-stream, as a DTS 96/24 stream's does where its decoder falls back to the 48 kHz core of a damaged frame, the decode converts the audio at the other rate to the rate the stream started at, on the stream's timeline; audio at that rate passes through untouched. The spectrogram, the overview and waveform detail all decode this way. The spectrogram's frequency mapping, grid and crosshair use the rate of the analysis session whose columns it shows; playback's rate stands in only until a session has supplied one, so a rate playback reports for a few frames redraws nothing. Waveform detail preserves missing coverage separately from actual silence.

The analysis control thread owns track identity, display settings, generation changes, and gapless staging. It is the only thread that creates generations, and it neither reads files nor waits for the library database: a file helper thread reads file stamps, probes formats, and keeps decoded overview waveforms in memory and in the database. Stopped staging threads are not waited for until shutdown. A spectrogram worker owns its decoder, FFT scratch storage, peak-hold state, and partial output batch. For a stream of four or more channels that it decodes itself, it splits the channels between itself and up to two helper threads of its own, a batch of 64 FFT rows per channel at a time, and interleaves the columns in channel order, so the output is the one a single thread computes; streams that GStreamer decodes already decode on a thread of their own and stay on the worker. On Linux the spectrogram worker, its helpers, the centered staging thread, and the overview decode thread run ten nice levels below the rest of the app, so they give way to the UI, render, and playback threads when the CPU is busy; the streaming threads of GStreamer's analysis pipelines are not lowered. Seeking resets these objects without recursive decode loops or rebuilding FFT plans. Rolling continuation uses a continuous column timeline; centered transitions use the new track's timeline. A continued file starts on that timeline where the previous file's last frame ends; the worker reports where when it opens the file, and the control thread adds that to the file's playback positions, using the previous track's last position only until the report arrives. A position before the file the worker decodes needs no seek: the previous file is still playing, or its columns are decoded already. A seek that a position needs on a continued timeline reads the file at the position less the file's start, and its columns stay on the timeline. A user seek is in the playing file and puts the session on that file's timeline; while the worker may be decoding another file, a staged successor or the track before the one playing, the seek restarts the session instead. The control thread counts a successor handed to the worker as possibly decoded until the worker reports that it went on with it or rejected it, or a new session opens the playing file: dropping the successor, as a stop near the end of a track does, cannot take it back once the worker went on with it. The worker reports the format of each file it opens, and the control thread judges gapless compatibility from those reports rather than from probes. A continuation whose file does not fit is not decoded: the control thread starts the file afresh at the playback position. A session that cannot read its file clears the spectrogram and reports the error to the user; the worker then waits for the next session. The worker reports every session that ends with no other to follow, a file it cannot open included, and the next seek, such as a stop's, starts a new session; a session parked at the end of its file takes seeks. A session that has to leave the columns it decodes for a playback position they cannot reach seeks where a restart would start: at the playhead when rolling, and before the left edge of the view when centered. It reports where, so the control thread judges later seeks by what is decoded. A seek, unlike a playback position, is passed on to the session as a seek. A rolling session always seeks for it. A centered session keeps its columns only if they cover the view of the target: the UI's ring still holds its left edge, and the playhead's column is decoded or next to be; otherwise it seeks before the left edge of the view at once, rather than decode every column up to it. Once the session has decoded the end of the file, the view it judges and seeks for ends there, as the UI's does, rather than at a duration the file or its decoder told. A seek outside the window a centered session was started for restarts it instead. A centered view takes a stop as a seek to the start, and playing the stopped track again as a seek to where it plays, so a ring that still covers the view keeps its columns; a rolling view's session restarts when the stopped track plays again. A centered session that starts left of its playhead, after a seek or a restart, decodes the playhead's columns first: from the playhead to 2 seconds past the right edge of the view, then the left of the view from where the session starts up to the playhead, then on from the right. Whenever playback brings the right edge of the view past what it decoded on the right, it goes back there before it finishes the left. Both sides are on the absolute column grid, and the session reports the end of its right side as what it has decoded. A right side that reaches the end of the file gives the file's extent, which every later chunk carries as its estimate, and the session publishes the end only once the left is sent: no column of a session comes after its end. A playhead past the end of the audio, where a duration estimated from a raw stream's bitrate can put it, gives a right side with no columns; the left then reaches the end of the file, and the session ends there, not at the playhead. A view that stops being centered does not get the rest of the left. The worker publishes a file's duration only if the file or its decoder tells it; raw AC-3 and DTS files tell it from their first frame header and the length of their frames, and until then a view has no end. Rolling sessions decode at twice realtime once the history a reset needs is filled, counting from the end of that refill.

## Ownership and backpressure

Spectral batches travel through a dedicated bounded channel to an FFI relay. Snapshot/control delivery remains independent. The relay serializes outside the UI queue lock and waits for queue space. The spectrogram worker is the only writer: the control thread hands it the chunks to emit before a session (staged columns, an immediate ring clear) with that session, so every chunk carries its session's generation and arrives in order. Generation changes discard obsolete output and interrupt blocked sends; shutdown wakes the relay explicitly. Rust and Qt must agree on command IDs, payloads, and FFI buffer ownership.

Settings → Spectrogram → “Limit to 22.05/24 kHz” (`spectrogram_frequency_cap`, off by default) ends the band a session sends at the audible band of the track's rate family: 22,050 Hz for rates that are multiples of 11,025 Hz, 24,000 Hz for the others, or Nyquist where that is lower, as for 44.1, 48 and 32 kHz. The FFT still computes every bin; the worker quantizes and sends those up to the cap, so the chunks, the FFI queue and the panes' rings take about half the bytes a column for a 96 kHz track and a quarter for a 192 kHz one. The bin count then no longer gives a bin's frequency, so every chunk also carries its FFT size, and Qt maps rows, grid labels and the hover readout at `sampleRate / fftSize` Hz a bin. Changing the setting starts a new session, as a change of FFT size does. A gapless continuation keeps its band, as it needs the same rate; a switch to a track of another rate starts a new session, and where its bin count differs, as between a capped 96 kHz track and a 44.1 kHz one, the rolling view's ring starts again from the new track, since a ring holds columns of one bin count.

| Storage | Policy |
| --- | --- |
| GStreamer analysis appsink | Bounded queue; producers wait instead of dropping audio |
| Spectral output channel | Four batches |
| Serialized FFI spectral queue | 16 MiB |
| Centered next-track staging | At most an 8 MiB prefix |
| Speculative spectral lookahead | 64 MiB across channels, subject to the minimum visible window |
| Waveform PCM cache | 32 MiB LRU of 16,384-frame tiles that windows read at sample resolution, plus the tile holding the end of the file and the tile decoded last; 2 MiB while only the level meter reads the file |
| Waveform summary cache, 64–512-frame levels | Separate 16 MiB LRU; 2 MiB while only the level meter reads the file |
| Waveform summary cache, 1,024–16,384-frame levels | 16 MiB for the open file, filled in order and never evicted |
| Those levels, waiting for a session of their file | 16 MiB and the PCM of the file's last tile, for one file: from the overview decode, or kept for the current track when its session closed |

The lookahead policy is shared by Rust and Qt through `ferrous_ffi_spectrogram_ring_capacity`. It preserves one viewport of history in centered mode and two in rolling mode, in addition to lookahead. A session decodes for the width of the view when it starts, at least 1920 pixels, and grows with a view that widens while it runs, as when the fullscreen viewer opens; every chunk carries that width, and a pane's ring holds at least what it needs, or what the pane's own width needs if that is more. A ring grows when either does and is sized again when a reset clears it, so after the viewer closes, the main window's panes keep the wider ring until a session for their own width clears it: in centered mode the next session, in rolling mode, which keeps its history across seeks and gapless transitions, the next one that clears it, such as a track change or a zoom. Visible-window requirements can exceed the speculative budget; this is not a hard process-memory ceiling. Decoder storage, render images, metadata, and allocations in flight are additional costs. While analysis is off, no pane holds a ring or a canvas.

These budgets bound what the app holds, and with glibc the process also gives back what it frees. glibc raises its mmap threshold to the size of each large block that is freed, up to 32 MiB, after which canvases, PCM tiles, FFI frames and queue snapshots all come from the malloc arenas, and the arenas keep what they free: a long session held hundreds of MiB of free heap. `main` therefore fixes the mmap and trim thresholds at glibc's default of 128 KiB before any thread starts (`ui/src/HeapAllocator.cpp`), which covers the Rust library as well, since it uses the same allocator. Blocks of 128 KiB or more get mappings of their own and go back to the system when freed. The free pages of smaller ones, such as library and queue strings and the spectrogram ring's 64 KiB blocks, stay in the arenas until a trim: `HeapTrimmer` calls `malloc_trim` on a worker thread of its own 5 seconds after the last track change, change of the queue's length, or departure of the main window from the screen. A trim walks every arena; in measurements it took 0.3–7 ms. A threshold set through `GLIBC_TUNABLES` is left as set. Other C libraries keep their own behaviour, and nothing is trimmed.

## Waveform queries

Detail requests run on Qt worker threads, which also parse the reply, so the GUI thread only takes the parsed window. While playing, nine tenths of a request's margins lie ahead of the view, which playback uses up; the next request goes out once less than 60% of a margin is left. Paused, the margins are even. A shared Rust service gives them one persistent decoder, held for one tile at a time, and caches PCM and min/max summaries; the level meter decodes between the tiles of a detail window. File identity includes path, length, modification time, device, inode and change time, so a replacement of the same length and time, such as an atomic save, is another file; one file is opened at a time. A cancelled request does not wait for the service; incomplete cancelled tiles are not cached. The summary pyramid starts at 64-frame blocks and supports coarser power-of-two queries without decoding again. Its levels from 1,024 frames up, about 6% of it, are kept for the whole file outside the LRU: whole-track and zoomed-out windows read every tile, and the full pyramid of a hi-res surround track (about 43 MB for five minutes of 96 kHz 5.1) does not fit the LRU, so they would decode the whole file each time. Once a window has read part of the file, a later window over that part at 1,024 frames a point or more decodes at most the two tiles its ends clip, and a whole-track window decodes nothing. The coarse budget holds about 26 minutes of 96 kHz 5.1, 13 of 192 kHz 5.1, or two hours of 44.1 kHz stereo; coarse windows over the rest of a longer file aggregate its fine levels if the LRU holds them, and otherwise decode it again. Clipped endpoints use PCM to avoid including samples outside the requested interval; a window that reaches the end of the file uses summaries for its last tile, and the PCM of that tile stays cached for windows that end just short of it. Only windows at sample resolution, below 64 frames a point, keep the PCM they read. A window of summaries builds the summaries of the tiles it decodes, its clipped end included, and keeps those, not the PCM: the next window of playback, or of the level meter, reads that end's summaries. The tile decoded last stays at hand, so a request that waited for its decode, or a window ending within it again, does not decode it twice.

The service keeps a session only while a reader in the UI needs it. A waveform view and the level meter each hold their file while they are shown in a window on screen; a hidden view, such as the one the spectrogram replaces, one in a window off screen, a hidden or stopped meter, and an item that moves to another file release it. While only the meter holds a file, the PCM and fine summary caches shrink to 2 MiB each, which its two-second windows need. Once nothing holds it, the session closes, with its decoder and caches; if the file is the current track's, its coarse summaries, the end of the file and the PCM of its last tile wait for the next session of the file, as the overview's do, so a whole-track view shown again decodes nothing, and a zoomed one decodes the tiles it shows. A track change drops what the service holds of another file that nothing reads, and keeps what waits for the track's own, as when it plays again. Readers retain and release on the GUI thread, a new file before the old one; closing a session, which stops a GStreamer decoder's pipeline, runs on the thread pool, and keeps what a reader retained since. A request still reading a closed session finishes with it, and a request whose reader went away while it opened its file keeps no session.

The overview decode of a track, which runs when the track has no saved overview, builds these coarse levels as well, up to the same budget, so the first whole-track window after it decodes nothing. It reads the packets of the decoder the service opens for the file and places them in tiles as the service's decoder does when it reads the file in order, before the overview's timeline fills gaps with silence, and builds their summaries with the same code, so they are the service's own: gaps stay missing coverage, and only tiles that hold audio are kept. Only a decode that reaches the end of the file hands them over, with the end of the file and the PCM of its last tile, and it does so before its last update. They go to the service's session of the file if one is open, or else wait for the session that opens it. A session takes them only if the identity of the file, read from the handle the overview decoded, is its own, and the decoder, rate and channel count are those it reads with; summaries of its path that do not match are dropped. A session's identity is that of a handle it opens before its decoder opens the path; if the path holds another file once the decoder has opened it, the session takes no summaries. A file that Symphonia opens but reads no audio from is read with GStreamer, and the session reads its first audio when it opens, so it knows which decoder reads the file. A cancelled, superseded or failed overview hands nothing over, and summaries no session took are dropped when another track loads.

The waveform editor has at most one detail request in flight. While playback moves the view on, that request stays as long as it covers part of the view, and its arrival asks for what it misses. A zoom, a resize, another track, or a seek to a view it does not cover cancels it.

At a deep zoom, playback can move the view past its detail before the next window arrives. Until it does, the view shows what it has. Samples drawn directly are drawn from the detail that still overlaps the view, and playback tiles stay while one is in view. The rest of the view stays empty. A raster that playback has left is drawn again only after a new window arrives or a request fails. Without that limit, a fullscreen view would draw and upload a raster of up to 59 MB on every frame. A seek, pause, zoom or resize still redraws it at once. A zoom out whose detail is not there yet keeps showing the deeper zoom. Playing, it switches as soon as the detail arrives, because playback tiles or samples draw it from then on. Paused, or for the whole track, the new zoom's raster is drawn a part each frame and shown once complete.

Native channels and the arithmetic downmix have separate extrema: averaging channel extrema would destroy phase cancellation. The versioned WVF2 payload carries both. The compact whole-track overview remains a separate background job with a persistent cache, partial-coverage metadata, and peak-preserving reduction. It takes the peak of every decoded sample at the stream's own rate, whether Symphonia decodes the file or GStreamer does, in the analysis's pipeline. Its decode sends the first preview as soon as it has peaks enough to show, and later ones at most every 240 ms; a preview covers only the audio decoded so far. Only an overview whose decode reached the end of the file is saved, with the seconds it covers; one that an error stopped shows what it covers and is decoded again the next time the track plays. Loading a saved overview counts as a use, and the cache keeps the 4,096 used last.

## Channel positions

Channel positions are probed on the metadata worker using the same decoder selection as visualization analysis. The metadata protocol carries labels in native PCM channel order. Recognized speaker sets restore the status layout name and icon; unknown layouts retain the channel count. Waveform and spectrogram labels use the reported positions, falling back to numbers for unknown surround positions. Late layout metadata updates the lane labels without replacing panes or clearing their history. The meter's columns take the lanes' labels in their tooltips and accessible names.

## Level meter

Each lane of the visualization, in the main window and in both viewers, carries the meter's 10-pixel column at its right end: a 1-pixel seam, then a 9-pixel vertical meter. Settings → Display → “Show a level meter at the end of each lane” controls it and is persisted as `show_level_meter`. It is off for a new install; a settings file without the key, from a build that showed the meter by default, keeps it on (`config::parse_settings_text`). While the option is on, the column is reserved, also when nothing plays: paused or stopped, it is an empty trough; the plot narrows only when the option changes, never on play, stop or the end of a file. Hiding the meter clears its source, cancels pending queries and releases its file in the waveform detail service. One lane shows the loudest of the channels; a lane per channel shows its own.

The meter reads source levels before listening volume and channel mute/solo. It reuses the waveform service through the existing WVF2 interface, requesting at most 2,048 extrema points over two seconds on a Qt worker thread. One request may be in flight, with one current window and one staged replacement. Cancellation and generation checks discard results after seeks, track changes, pause, or hiding the view; failed reads retry after a delay. Only bins whose end has reached the transport playhead contribute to the display.

The scale runs from −60 to 0 dBFS, its listed levels evenly spaced: −6, −12, −24 and −48 dB at four fifths to one fifth of its height. The fill rises from the bottom in the plot's `meterFill` over its `meterTrough`, with 1-pixel gaps in the plot's floor colour at −6, −12 and −24 dB (−6 and −24 in lanes under 64 pixels), a full-width 2-pixel peak tick, and a 3-pixel clip lamp at the top that lights for 2 seconds after a bin at full scale; its tooltip and accessible value say “clipping”. Each channel has immediate attack, 20 dB/s release, and a peak held for 1.5 seconds before falling at 20 dB/s. Elapsed-time ballistics apply each bin when it ended, so changing display refresh rate does not change hold or decay. Every bin since the previous frame counts once, also after the meter has been idle, and pausing or resuming first brings the levels up to that moment. During playback the columns show the levels as of the newest bin heard, not partway into the next, so a steady signal draws steady columns. The scene graph draws rectangles only; fills and ticks end on device pixels. A frame is requested only when a fill, tick or lamp changes by a device pixel, or on a resize or scale change. Each presented frame advances the meter; with nothing to draw, a single-shot timer wakes it for its next change: the next pixel of a decay, the end of a peak hold or of the clip lamp, computed in closed form, or, during playback, the first upcoming bin that changes a column, found by looking up to 0.5 seconds ahead in the current window. Steady levels, silence, held peaks, and a settled pause or stop draw no frames, and a settled pause or stop leaves no timer running. Pause lets the levels and held peaks decay; stop and transport discontinuities clear them. Exact levels go to a reader, the column's tooltip or assistive technology, at most four times a second, and only while one reads them.

## The plot layer

Labels, the Mute and Solo buttons, the mode switch, the meter and the pane's states are one layer over whichever plot shows (`ui/qml/viewers/PlotLayer.qml`), in the plot's own colours (`UiPalette.plotColors`): a fixed set on the spectrogram, which looks the same in both themes, and the view's on the waveform. Lanes share one layout, a 1-pixel seam on the rows at k × height / lanes (`ui/qml/logic/PlotLanes.js`, `LevelMeterItem::laneRows`), which the waveform's own seams follow. The spectrogram's scale, when it is on, is drawn by `SpectrogramItem` as outlined text in cached textures: frequency labels with their unit and a 6-pixel tick at the right edge, skipped within 34 pixels of a lane's top, and time labels with a 5-pixel tick along the top of the first lane, 10 seconds apart at zoom 1, clear of the left edge and of the mode switch. The waveform has no scale. The crosshair's readout is drawn on the plot, as the waveform's is, on plates in the plot's colours that clamp inside the lane (`ui/src/CrosshairReadout.h`): the frequency and level on the hovered lane's right edge at the horizontal line, left of the frequency scale while it shows, and the time on the lowest lane's bottom edge at the vertical line. Each plate follows only its own line, so neither jumps: the value stays above the time where the lane is tall enough, and in a lane too short for that the time stops at the value's left edge; it also stops right of the lowest lane's label and Mute and Solo buttons (`PlotLayer.lowestLaneHeadBounds`), and neither plate goes under them. A plot too narrow for both plates leaves one out, the same one wherever the pointer is: the value where the time fits neither above nor beside it, and the time where it doesn't fit right of the lane head on its own. Whether a plate fits goes by the widest text it can show, with each digit the font's widest, so a plate doesn't come and go as the level and time under the pointer change. Left of a gapless boundary, the time is the previous track's. `SpectrogramItem` lays the plates out with the crosshair and hands their text to the GUI thread (`crosshairReadout`) only when it changes. When the overview decode finds that a lossless or PCM file's timeline ends before the length its header gives (the end of the last packet that decoded, so a damaged packet inside the file is a gap, not an end), the analysis reports it once per play as a warning in Recent Issues and flags it in the analysis frame (`ANALYSIS_FLAG_WAVEFORM_ENDS_EARLY`), with the cut as the waveform's coverage. Analysis snapshots and frames carry the track token they are of: the bridge applies a snapshot only to its own track, so one of the track before that waits in the queue at a track change, Repeat One's included, cannot mark the next; the UI ignores a frame of a track older than the one playback has told it of; the pane shows “The file ends at m:ss.” in the empty part of the plot after the cut, which the plot items report as `markerX` only when it moves by a pixel. Such a file's overview is not saved, so every play finds the cut again.

## Qt rendering and visibility

Each spectrogram item owns its raw ring and rendered canvas under its state mutex. The ring takes memory in blocks of 64 columns, each when one of its columns is first written, so making room for a ring on a track, mode or FFT size change costs the GUI thread nothing however large the ring is; columns not written yet draw as missing. A rolling ring is written in the order the columns arrive. A centered session's ring keeps each column at the write sequence of its offset from the session's first column, which the worker's reset gives, so that the columns left of the playhead, which arrive after those right of it, land where they belong, and the ring drops the columns furthest left first; a column further left than the ring reaches from its newest is not written. Matching panes share immutable frequency-bin projection ranges and color lookup tables through weak references. Render passes retain their projection; image updates preserve previously retained `QImage` copies. This shares reusable rendering calculations without introducing a second global owner for mutable timeline state.

A window is on screen while it is visible, not minimized, and exposed (`WindowPresence`). On Wayland, xdg-shell has no minimized state, so a minimized window keeps reporting the visibility it had; Qt marks it unexposed once the compositor stops answering its frame callbacks, as it does for a minimized window, one on another virtual desktop, or one whose display is off. A window that stops being exposed stays on screen for two more seconds, so that a brief unexposure, such as a desktop switch or a live resize, stops and restarts nothing; one exposed again is back at once. `BridgeClient` coalesces item and window changes and enables spectral analysis when at least one registered item is visible in a window on screen. Hiding all views stops decoding, cancels staging, and advances the generation. Transport and track changes still update analysis state. Showing a view starts a fresh generation at the latest position, including a viewport of rolling history. When analysis stops, every spectrogram pane frees its column ring and canvas and takes no columns until analysis starts again; its textures go with its scene node if its window still draws. A pane hidden while another keeps analysis on keeps its columns, so showing it again restarts nothing for the panes on screen. Analysis counts the times it stops and publishes the generation the latest stop made (`ferrous_ffi_bridge_spectrogram_stops`). No session starts while it is off, so `BridgeClient` drops every spectral frame from the stop until one newer than that generation arrives, waiting for the count to reach its own stops first; frames still on their way from before the stop, resets included, never reach the panes. The non-Qt analysis API defaults to enabled.

A hidden pane skips animation ticks and canvas writes while retaining batches needed by another visible pane. Showing it invalidates the canvas. Hidden waveform surfaces clear their detail source, cancelling detail queries and releasing their file in the detail service (see Waveform queries); the one-off overview cache job remains independent. A spectrogram pane or waveform editor that is hidden, such as the view the other visualization mode replaces, or that is in a window off screen asks for no playback frames: it cancels the frame it waits for and follows the clock without frames, through seeks and track changes, including a gapless successor or Repeat-One. Shown again, it asks for one frame, which draws playback where it is then, and its frames follow from there. The waveform editor also decodes no detail then: leaving the screen cancels its request in flight and releases its file in the detail service, and neither the clock nor its frames ask for another; it keeps the detail it has, and shown again asks for the detail of its view if that does not cover it. The level meter in a window off screen clears its levels and cancels its queries, as when it is hidden. Qt asks a hidden item for its scene node as well, whenever the item changes or enters another window; a hidden waveform editor keeps the node it has and draws nothing into it, so the waveform that the spectrogram replaces does not draw a whole screen into the fullscreen viewer's first frame.

The fullscreen viewers' windows are made the first time each viewer opens over the whole screen, not at startup, and are only hidden when it closes. Qt keeps the graphics context and the scene graph of a hidden window, so a viewer that opens again sets neither up again. The views it shows still make new textures in it, as in any other window: each window draws with a context of its own, on a render thread of its own. A hidden viewer window is off screen, as a minimized one is.

During playback the spectrogram and the waveform editor ask for a frame only when it would differ from the last one. A zoomed waveform that follows the playhead moves by whole device pixels: its view starts on a device pixel of the track's own grid, with the playhead on its middle pixel, and moves on a pixel when the playhead reaches its next one, so the frames between are the same and it changes only at those steps. A spectrogram that scrolls, rolling or centered, moves by whole device pixels: its canvas stays on the pixel it has reached until the scroll has gone a whole pixel further, so the column under a centered playhead is the one playing, as in a view that stays still. It changes only at those steps and when playback reaches the next column, which comes in at the right edge. A centered spectrogram that stays still, such as one showing the whole track, and a waveform showing the whole track or one of its ends, change only when the playhead reaches its next pixel or the view starts to follow it. The item works out, from the frame it last drew, when playback reaches that point on the clock's course, and wakes its frame with a single-shot timer; a frame that is already due is asked for at once. The spectrogram panes and the waveform editor of a window share one timer, with their frames due on a grid of whole milliseconds, so views whose pixels change together are drawn in one frame of the window. While playing, a waveform that scrolls faster than 4,000 logical pixels a second, its pixels a sample times the track's sample rate, is drawn at most about 120 times a second, where every refresh would draw a texture moving too fast to follow: on every n-th refresh of its window's screen, n the whole number nearest the refresh rate over 120, so that its frames are evenly spaced. That is every 3rd refresh at 360 Hz, every 2nd at 240 Hz, and every refresh at 144 Hz and below. The cap comes on above 4,000 px/s and goes off below 3,200 px/s, so that a zoom near the threshold does not switch it back and forth, and it follows the window to another screen and the screen's rate as it changes. Capped frames keep to a grid of their interval from the first, so that a timer that wakes a little late delays only its own frame; one a refresh or more late, or a frame drawn at once, starts the grid again from itself. A pause, a resume, a seek, a track change, a zoom, a resize and an edit are drawn at once, whenever the next capped frame is due; a playback tile or detail window that comes in between shows with the next capped frame. A spectrogram showing a zoom preview, or holding its position until data arrives, asks for every frame, as does a waveform while it draws a cache over several frames; a playback tile that a worker has made asks for a frame of its own, or hands a zoom over. After a seek outside the decoded columns, a centered pane shows its previous image until the playhead's column arrives; the columns left of it then draw as missing until they arrive. A zoom shows its preview until its data covers the whole view. A clock sample that only corrects the course reschedules that frame; a seek, a track change, including a gapless successor or Repeat-One, and a pause show at once. Data, rasterizations, and property changes still ask for their own frames, except columns that a playing spectrogram receives ahead of the last ones it shows: they show only once playback reaches them, in frames it has already asked for. Texture nodes are only changed when their texture or placement does, so a frame that moves only the playhead leaves the canvas nodes alone.

With OpenGL, a pane's canvas is one OpenGL texture of the item's own, kept from frame to frame and split only where the canvas is wider than OpenGL's largest texture; Qt's scene graph draws it through `QNativeInterface::QSGOpenGLTexture`. While the scene graph synchronizes, with its context current, a frame uploads into it with `glTexSubImage2D` the canvas columns drawn since the last frame, in the order they were drawn: a rasterization's canvas first, whole, then the columns drawn over it since. Two spans of the texture draw the ring across its wrap and a third the newest column, all with one texture, so the renderer can batch them, and scrolling moves only those spans. A new scene graph or window makes new textures from the whole canvas; the old ones are deleted with their own window's context. Qt's public API cannot update part of a texture with other renderers, so they get the canvas in tiles of 64 columns, each made again when one of its columns changes; so does a canvas taller than OpenGL's largest texture, whose tiles Qt scales to fit.

The playback clock's own properties, which QML binds, change only when a view would show it: its text once a second, and its position by the step the transport bar asks for, a device pixel of the seek bar. The clock works out when playback reaches the next of either and wakes then with a single-shot timer; a seek, a track change, a pause, a resume or a change of the step shows the exact position at once. What starts from the position, such as a relative seek or a step of the seek bar's keys or wheel, reads the exact position from the clock on demand. A main window off screen (see above) turns off the clock's timer. Its properties then follow the engine's samples, and catch up when the window is back on screen, so the transport bar and the status bar show the position at once. MPRIS reads the clock directly, and Last.fm's scrobble timing follows the backend's playback state, so neither depends on those updates.

## Validation and profiling

Run the checks in [DEVELOPMENT.md](DEVELOPMENT.md). Regression fixtures are synthetic or embedded and require no personal media or network access. Tests cover rolling and centered seeks, codec preroll, packet boundaries, timestamp gaps, track transitions, EOF, cancellation, stale generations, memory budgets, and Rust/Qt waveform payloads.

The optional [spectrogram benchmark](DEVELOPMENT.md#profiling) measures CPU canvas rebuilding with resident data. Its image checksums permit output comparisons. It does not measure decoder throughput, transport latency, GPU uploads, or end-to-end frame pacing; those require an instrumented application run on the target hardware.
